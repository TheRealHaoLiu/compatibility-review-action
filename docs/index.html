1 · What the bot does

One note per pull request, three possible verdicts

Compat-review reads a pull request and appends an upgrade-compatibility note to it. The note is advisory and never blocks a merge. It answers one question for the human reviewing the PR: will something that works today in a customer installation stop working after this change ships?

Red

A configuration already stored in installations stops working after upgrade, with no action by the operator.

Reviewer: confirm the break, look for an alternative that avoids it, and confirm with the PM before merging.

Yellow

Behavior changes worth knowing about, but stored configuration keeps working: validation on re-save, limits on new input, changes to output or access.

Reviewer: read the note; decide whether a release note is needed.

Green

No behavior change for existing installations.

Reviewer: nothing.
2 · How it decides

Facts from the model, verdict from a fixed rule

The model does not pick the verdict. It reads the change and answers six factual questions. A short fixed rule, written in code, turns those answers into Red, Yellow, or Green. Every Red can therefore be traced to a specific setup that breaks and the reason it breaks, and the rule can be adjusted without changing the prompt.

The six questions

  1. What existing setup, if any, stops working? Named specifically, or "none".
  2. Does the change alter something that already exists, or only add something new?
  3. Does the change itself keep the old behavior working, for example through a migration, a fallback, or a flag?
  4. How common is the affected setup: common, uncommon, or rare?
  5. Does the change widen who can do what, or change output that other systems read?
  6. How does the break happen? A new restriction on configuration already stored, a check that runs only when the configuration is saved again, a limit on new input only, a permission change, a removal, a changed default, or a changed output.

Why stored configuration gets special treatment. How common a setup is cannot be judged from a diff. So the rule does not depend on that answer for the most damaging case: a new deny-list, validation rule, or filter applied at runtime to configuration customers already have stored. The stored value stays in place and silently stops working the next time it is used, however rare it is. A check that only runs when someone saves the value again is Yellow, because existing configuration keeps working until then. The rule makes no judgment about whether the blocked value is a reasonable setup.

More context than the diff. Before the model reads the change, tooling adds the code around each changed spot and the places that call it, taken from the tree before the change. No model call is involved. This is how the model can tell that a validator runs when a job launches rather than when a setting is saved. The input is about one and a half times the diff.

One review per pull request. In production each pull request is reviewed once. The benchmark reviews each one three times to measure how consistent a single review is; the consistency numbers are in Results.

3 · The benchmark

198 labeled pull requests from one repository

198 merged pull requests from the Ansible Automation Platform controller repository, each labeled breaking, notable, or none under the same written criterion the bot applies.

Labels. The labeled set was created by two models, Opus and Sol, followed by human review. Each model answered the same six questions for every pull request, a human reviewed every label, and disputed cases were ruled by the maintainer, with each ruling and its reason recorded. Writing the v9 criterion down moved seven labels to breaking and nine to notable. The queue of unreviewed labels is empty.

Second repository. 24 pull requests from django-ansible-base, graded by their author, none breaking. Used as a check on false alarms in a second codebase.

Measures

  • Red on breaking: the share of breaking PRs shown Red.
  • Escapes: breaking PRs shown Green. The one number that must stay at zero.
  • False Red: none PRs shown Red.
  • Red on notable: PRs the reviewer should read but that are not breaking.
  • Stream mix: Red, Yellow, and Green per 100 pull requests from the random sample.
  • Red precision: the share of Reds that are breaking, and the share that are breaking or notable.
  • Consistency: every PR was reviewed three times; the share of PRs that get the same verdict in all three runs.
  • Cost: tokens and dollars per run at list price.

5 · Known limits

Where it still misses, and why

  • Three of 34 breaking PRs are not Red in every run. Two are permission changes, which the criterion covers only through prevalence; they are Red in one and two runs of three and never Green. One depends on a runtime path that lives in an earlier PR's code, so its own diff reads as re-save in every run.
  • Between 7 and 10 of 96 none PRs are Red in a given run, three of them in every run. All are prevalence judgments: the model called the affected setup common where the label says otherwise.
  • Yellow lands on 32 of every 100 random PRs. That rate follows from the definition of notable, not from the model, and is where reviewer fatigue would come from.
  • Prevalence is still a model judgment wherever the mechanism clause does not apply, and it is the source of the remaining false Reds.
  • One repository, plus a 24-PR check on a second. Base rates are the controller's. Enriched context was built only for the controller in the benchmark; in CI the checkout provides the tree for any repository.
6 · Feedback loop

Every review is a gradable record

Alongside the note in the PR description, the bot posts one comment on the PR carrying what a grader needs later: the bot version (prompt, rule, and model configuration), the commit it reviewed (PR head SHA and base SHA), the verdict with its one-line reason duplicated from the note, and an invitation to the reviewer: thumbs up if the verdict is right, thumbs down if it is wrong, and a reply saying why.

Extraction. A script lists the bot's comments across a repository, reads the reactions and the replies, and produces a grade sheet per repository and bot version: agreement rate, and every downvoted case with the reviewer's reason. Downvotes with a reason become new benchmark cases in the reviewer's own words. That is how the rule and the prompt get tuned per repository.

PR conversation comments on GitHub are flat, so a reply is matched as a later comment on the same PR that mentions the bot or quotes its comment.
